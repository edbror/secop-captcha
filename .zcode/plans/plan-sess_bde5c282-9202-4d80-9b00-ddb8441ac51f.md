# Fix secop-captcha: stop burning tokens, make the farm path actually work

**Branch:** create `fix/captcha-solve-flow` off `master` before any changes. The current uncommitted files (`demo-screenshot.js` mod, `solve-now.js`, `solve-live.js`, `test/real.test.js`) carry over to the branch; the ad-hoc solve scripts get folded into the new `test/live.test.js` and removed.

## Context

The service "works by definition" (farm returns tokens, endpoints respond) but the captcha is never actually solved end-to-end. Root causes found in audit:

1. **`/solve` consumes the token it returns** (`src/server-ponytail.js:268-285`): `checkWithSecop(token)` submits the token to SECOP's `CaptchaCheck` before returning it. reCAPTCHA v2 tokens are **single-use** — SECOP siteverifies server-side. The scraper then re-submits the same token → duplicate → rejected.
2. **The service's own SECOP check can never succeed** (`src/solver-ponytail.js:214-252`): `fetchSecopMkey()` runs in a throwaway session (no cookie jar), `CaptchaCheck` is hit from a different fresh session, and the `DEFAULT_MKEY` fallback (line 39) is a stale October snapshot. Proof: scratch captures show SECOP answering *"Esta página ha expirado por inactividad"* ErrorPage. This poisons `/solve` and `/verify` responses with `secop.success:false` even when the farm token is good.
3. **Scraper submits with a stale mkey** (`secop-scraper/secop.py:447-507`): the captcha page (holding the mkey) loads *before* the farm solve (10–120s); the mkey can expire by submission time. The user's own `demo-screenshot.js` run today had the same bug class (token from browser #1, submission in browser #2).
4. **Local Puppeteer path gets image challenges** it can't handle (documented by the Oct 28 QR/image-grid scratch investigation), and its token poll is only 3s (`TOKEN_MAX_POLLS=15 × 200ms`).
5. **CapSolver fallback is doubly broken**: `.env` key is a placeholder (`CAP-1D...n`); task type `CapSolverRecaptchaTaskProxyless` is not a valid CapSolver type (should be `ReCaptchaV2TaskProxyLess`).
6. **2Captcha error handling masks real errors** (`src/solver-ponytail.js:73-82`): checks `submitBody.error`, but 2Captcha JSON errors are `{status:0, request:"ERROR_ZERO_BALANCE"}` → error string gets treated as a captcha ID → surfaces later as misleading `ERROR_WRONG_CAPTCHA_ID`.
7. Minor: concurrency counter decrements synchronously so it never gates (`server-ponytail.js:414-437`); `/solve` always returns `success:true` regardless of outcomes; Dockerfile sets `VERIFY_WITH_GOOGLE=true` (guaranteed-failing check); `/redirect` echoes the stale `DEFAULT_MKEY`.

The only flow ever proven to work (scratch `test_access.js`, demo video Oct 28): **one session, fresh mkey, single submission**. The fix restores that invariant across the service ↔ scraper boundary.

## Changes

### A. Service: `src/server-ponytail.js`
- **`handleSolve`**: remove `verifyWithGoogle` + `checkWithSecop` from the response path entirely. New response: `{success, token, method, farm, solvedAt, expiresIn: 110}`. `success` = the solve actually returned a valid token. This is the core fix — the token reaches the scraper unconsumed.
- Keep `MOCK_SOLVER` support (document it in `.env.example`).
- Fix the concurrency gate: decrement in `res.on('finish')` instead of the synchronous `finally`.
- `/redirect`: stop echoing `DEFAULT_MKEY`; return the live mkey via `fetchSecopMkey()` (or omit the field if extraction fails).
- `/verify`: keep, but label the response `destructive: true` — it consumes the token by design (uses `checkWithSecopBrowser`).

### B. Service: `src/solver-ponytail.js`
- **`solveVia2Captcha`**: detect submit errors correctly (`status===0` or `request` starting with `ERROR_`); add a `get2CaptchaBalance()` helper (free `res.php?action=getbalance`).
- **`solveViaCapSolver`**: change task type to `ReCaptchaV2TaskProxyLess` (verify against current CapSolver docs during implementation).
- **Remove `DEFAULT_MKEY` silent fallback**: mkey extraction failure now throws with a clear message.
- **`solveWithPuppeteer`**: extend token poll to ~30s (e.g. 500ms × 60); detect the challenge frame (`recaptcha/api2/bframe`) appearing after the click → fail fast with "image challenge served — use method=service (farm)".
- CLI: add `balance` subcommand; make `check`'s output honest (it's a destructive, session-bound check).
- Remove the no-op ternary (line 99) and fix the misleading skipped-Google log lines.

### C. Scraper: `secop-scraper/secop.py` (`_inject_token`)
After the token arrives: re-navigate the captcha page **in the same Playwright session** (fresh mkey, session kept alive), inject the token, and navigate to `CaptchaCheck` immediately — then explicitly `page.goto` the target document URL for the retry. Log the landing URL after `CaptchaCheck` for diagnosability.

### D. Config & docs
- `.env.example`: document `MOCK_SOLVER`; note `CAPSOLVER_API_KEY` is currently a placeholder (either supply a real key or remove it so fallback fails loudly).
- `Dockerfile`: drop `VERIFY_WITH_GOOGLE=true`.
- `README.md` / `INTEGRATION.md`: new `/solve` response shape; the token lifecycle rule (single-use, ~2 min, must be submitted by the caller's session with a fresh mkey); update the Python-client contract notes.

### E. Tests
- `test/solver.test.js`: rewrite with **mocked `fetch`** (no network, no cost): 2Captcha happy path / `CAPCHA_NOT_READY` loop / `ERROR_ZERO_BALANCE` / poll timeout; CapSolver create+poll; `solve()` cross-farm fallback; `shouldSkipGoogleVerification`.
- `test/e2e.test.js`: update to the new response shape (no `google`/`secop` fields on `/solve`); keep auth/validation/CORS/header coverage.
- New `test/live.test.js` (replaces `test/real.test.js` + `solve-now.js`/`solve-live.js` ad-hoc scripts): staged live verification (see below).
